A single stuck transferStore call can freeze a pool migration permanently
  - Each migration pass (MigratePoolToSetDurableTask.processNext) starts at most one
    transfer by calling client.transferStore in tryStores and *waiting for its Future*
    before the pass is allowed to finish
  - transferStore is a transaction that updates the source and destination device
    objects. It runs under transactUntilSuccessfulWithRecovery, which retries forever
    on any error not classified as StopRetrying. Only NoSuchElementException,
    InvalidDestination, StoreNotActive and DeviceFailed give up. Anything else
    (a persistently colliding or unreachable device object, a host that never answers)
    is retried with no attempt limit and no deadline, so the Future never completes
  - While that Future is pending the pass never ends, and three things then keep
    anything else from happening:
      1. the single-flight guard (boundedSingleFlight) stays set, so every poll tick
         is dropped
      2. the next poll is only armed by scheduleRecheck at the end of a pass, so no
         tick is scheduled at all
      3. SystemTaskRunner.heartbeat() bumps every *running* task whether or not it is
         making progress, so the service never decides the task is dead and
         re-dispatches it. A retarget of the migration cannot rescue it either,
         because it is only noticed at the start of a pass
  - The result is a migration that shows as running forever and moves nothing
  - Contrast SetRebalanceDurableTask, which fires transferStore without waiting
    and reschedules immediately, so the same stuck call cannot stall it
  - The retry loop is the right recovery for genuinely transient faults, which is
    why it was left alone. The fix is to stop the pass from depending on the
    call's completion (fire and let the next poll observe the device entries, as
    the rebalance task does) or to give the call a bounded number of attempts
  - Deliberately split out of the parallel-store-transfers work
    (docs/superpowers/specs/2026-10-24-parallel-store-transfers-design.md)

StoragePool.getState() and dropCachedState() are now dead API
  - SimpleStoragePool caches its StoragePoolState at construction and
    dropCachedState() has never had a caller, so the cached copy was a
    permanent snapshot of where the stores were when the client first
    touched the pool
  - Both stale-mapping consumers were fixed to use
    AspenClient.getStoragePoolState instead: transferStore and
    StoreManager.startStoreTransferOut. A survey of src/main and src/test
    found no remaining getState() callers
  - storagePoolCache still memoises the SimpleStoragePool instance, but its
    other construction-time fields (ida, maxObjectSize, allocStrategy,
    allocStrategyConfig, pointer) are immutable per pool and no consumer
    reads a store-to-device mapping from them
  - So this is now a cleanup, not a correctness issue: either delete
    getState()/dropCachedState() or wire the invalidation up

Possible bug in AmoebaFS
  - Looks like UnlinkFileTask may double-decrement the inode number
  - prepareUnlink method decrements the inode number and creates the UnlinkFileTask atomically
    if the refcount is zero.
  - The task always decrements the refcount as the first step
  - Need to verify that this is a flaw and look for cases where the task doing the decrement is
    valid. If never valid, just skip the decrement step and move on to freeing resources.
