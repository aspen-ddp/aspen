- Backlog issues

ZMQNet.ioThread leaves a half-built host behind when NewHostAvailable fails
partway through
  - The send-queue loop now guards each item, so a throw here no longer takes
    the IO thread down with it. What survives depends on where it threw, and
    neither state ever heals
  - Fail at setIdentity or connect and entry.odealer stays None. The created
    socket leaks until the context closes, and every later message to that
    host piles into entry.pendingMessages, which nothing will drain:
    MetadataManager already holds Right(entry), so no second NewHostAvailable
    is ever enqueued
  - Fail at either send and the dealer is live and in connectedDealers, but
    connectedHosts and rebuildPoller were skipped. The host is sendable yet
    never polled, so its inbound traffic is discarded forever and nothing
    ever marks it offline. This is the state a dealer.send failure actually
    produces, and it is the worse of the two
  - Likely fix is to move both sends after the connectedHosts/rebuildPoller
    registration, which does not depend on them and cannot reorder anything
    because every send on this path runs on the one IO thread. That leaves
    only the narrow setIdentity/connect window, which wants the socket closed
    on the failure path -- and a seam that lets a test make connect() fail.
    The dealer is built inline from context.createSocket on the IO thread and
    there is no ZMQNet harness to drive it, per the untested entry below
  - SendToClient has a narrower variant: a throw from router.send(encoded)
    leaves an unfinished multipart message on the ROUTER, so the next
    SendToClient appends its identity as frame 2 of the stale frame 1. One
    client gets a garbled body, one gets nothing. The encode is hoisted above
    the first frame so encodeClientResponse cannot cause this, but the second
    send still can. Bounded (the next SendToClient clears it) and accepted

A createHostEntry that throws late orphans the entry the IO thread already
accepted
  - createHostEntry enqueues NewHostAvailable before the wakeIoThread() that
    can throw, so a throw from that wake still leaves a fully live entry
    behind: the IO loop drains sendQueue on every iteration regardless of the
    wake, so the dealer is created and registered in connectedDealers, the
    entry is added to connectedHosts, and both are flushed and heartbeated
    thereafter
  - Meanwhile MetadataManager's guard has removed the host from its map, so
    the next send builds a second entry and a second dealer for the same host.
    The first is unreachable from the manager but still live in the IO thread
  - This is the accepted cost of the guard -- an orphaned entry beats a
    permanent wedge -- and reachability is low, since wakeIoThread fails on a
    closed socket, i.e. during teardown of a process that is exiting anyway.
    Recorded rather than fixed
  - Candidate fix is for createHostEntry to swallow a wakeIoThread failure
    rather than propagate it. The wake is best-effort: the IO loop drains the
    send queue unconditionally every iteration, and poll() never waits longer
    than the next heartbeat, so a missed wake delays delivery by at most one
    heartbeat period rather than losing it. Swallowing makes the orphaned
    entry and the duplicate dealer impossible, and needs no test seam. The
    same change to storeResolved, whose wakeIoThread is likewise unguarded,
    would retire the handoff residue the MetadataManager guard now absorbs
  - Distinct from the leak above: there NewHostAvailable fails, here it
    succeeds for an entry the manager has already forgotten

ZMQNet.heartbeat can still kill the IO thread
  - heartbeat() calls dealer.send on every connected host from inside
    ioThread's loop, outside both the per-item send-queue guard and the poll
    guard above it. A throw while not shutting down matches neither handler,
    so it propagates out of ioThread and the thread dies -- the exact failure
    the send-queue guard was added to prevent, one screen higher in the same
    method -- and unlike the two above it runs every heartbeat period, not
    just on host setup
  - Deliberately not fixed alongside the send loop, because the recovery
    differs: a bad queue item is dropped, whereas a host whose heartbeat
    throws needs a decision -- skip it this round, or mark it offline

ZMQNet.ioThread's failure handling is untested
  - There is no ZMQNet suite. ProtobufMessageCodecSuite is the only file under
    zmqnet/, and ZMQNet's constructor binds real sockets, so covering the
    guards would mean standing up a harness or extracting a seam
  - The per-item send-queue guard therefore shipped without a test. That is a
    decision rather than an oversight, and it is also why the half-built host
    entry above is recorded rather than fixed: that fix wants the same seam

A pool stuck at migration InProgress cannot be re-driven through the public
API
  - migratePoolToSet only enrolls a MigratePoolToSetDurableTask when the pool
    is not already InProgress. Once it is, a same-set call is a no-op and a
    different-set call retargets without enrolling, so no call can arm a
    driver
  - If the task instance is ever lost while the pool is InProgress, the pool
    is wedged with no public recourse -- there is no way to clear the
    migration field or re-enroll
  - Not currently reachable. Enrollment is durable, so a crash is fine: the
    runner re-creates enrolled tasks on restart. The one path that
    deregisters without finishing is SystemTaskRunner.shutdown(), which
    fails the task's promise with TaskStopped, and onTaskComplete
    deregisters on failure too. That method has no production caller -- only
    SystemTaskRunnerSuite and SystemTaskExecutorServiceSuite
  - Candidate fix is to make enrollment idempotent and unconditional, or to
    enroll when the pool is InProgress but nothing is registered for it.
    Either removes the trap without needing shutdown() to change
  - Note that AspenClient.migratePoolToSet's docstring currently claims there
    is "no window in which a pool is InProgress with no task driving it".
    That is true of the start transaction but not of the shutdown path

MigratePoolToSetDurableTask awaits transferStore, so a stalled transfer
stalls the task permanently
  - SetRebalanceDurableTask fires transferStore and immediately reschedules;
    the migration task awaits the result because it needs the boolean to
    decide whether to advance to the next store
  - transferStore is transactUntilSuccessfulWithRecovery, i.e. unbounded
    internal retry. While it retries, the pass never completes, the
    ignoreExtraCallsWhileRunning flag stays set, and no poll is armed
  - Self-perpetuating: SystemTaskRunner.heartbeat() bumps every *running*
    task regardless of progress, so the service never re-dispatches it
    either, and a retarget cannot rescue it
  - Accepted for now. The retry loop is the correct recovery for genuinely
    transient faults, and every fast-fail case is already StopRetrying
    (NoSuchElementException, InvalidDestination, StoreNotActive)

StoragePool.getState() and dropCachedState() are now dead API
  - SimpleStoragePool caches its StoragePoolState at construction and
    dropCachedState() has never had a caller, so the cached copy was a
    permanent snapshot of where the stores were when the client first
    touched the pool
  - Both stale-mapping consumers were fixed to use
    AspenClient.getStoragePoolState instead: transferStore and
    StoreManager.startStoreTransferOut. A survey of src/main and src/test
    found no remaining getState() callers
  - storagePoolCache still memoises the SimpleStoragePool instance, but its
    other construction-time fields (ida, maxObjectSize, allocStrategy,
    allocStrategyConfig, pointer) are immutable per pool and no consumer
    reads a store-to-device mapping from them
  - So this is now a cleanup, not a correctness issue: either delete
    getState()/dropCachedState() or wire the invalidation up

The server-side transfer path has no integration coverage
  - startStoreTransferOut, transferDataReceived and createTransferOut are
    never exercised by any test
  - TestNetwork.sendHostMessage only appends to capturedHostMessages;
    nothing forwards them to receiveHostMessage, so StartStoreTransfer is
    captured and dropped. Tests that need a completed transfer call
    simulateTransferComplete, which short-circuits the real path
  - The startStoreTransferOut stale-source fix therefore shipped without a
    regression guard, resting on being mechanically identical to the
    transferStore fix, which was confirmed empirically by revert probe
  - Building the harness is a piece of work in its own right

A transfer whose source host dies mid-flight blocks its pool's migration
forever
  - The store is left TransferringOut, and MigratePoolToSetDurableTask's
    in-flight gate then refuses to start any further transfer for that pool.
    A retarget does not clear it
  - Pre-existing gap in the transfer subsystem, but migration is the first
    workflow whose *progress* depends on transfers completing
  - Related to the abortStoreTransfer note above

RebalancingServiceSuite leaks a 100ms pollPeriod when a test fails
  - Six sweep tests set RebalancingDurableService.pollPeriod to 100ms and
    restore it in the yield, so any failure earlier in the for-comprehension
    leaves the short period in place for every later suite in the same JVM
  - Pre-existing pattern (the original enrollment test does it too), but the
    blast radius grew with the sweep tests. A fixture-level restore -- or an
    andThen on the assembled future -- would make it unconditional

rebalanceStorageDeviceSet now walks the services TKVL on its no-op path
  - Splitting the entry point so the sweep can pass its own statePointer moved
    the pointer lookup above the pendingTransfers.nonEmpty short-circuit, so a
    set with a transfer in flight pays a multi-tier traversal to decide to do
    nothing, and returns a failed future rather than Future.unit if the service
    is unregistered
  - Bootstrap always registers the service, so the failure mode is theoretical;
    the wasted read is not. Reordering the short-circuit above the lookup fixes
    both

parseRebalancePeriod's range check is conservative for hours and minutes
  - checkDurationRange bounds days at the exact FiniteDuration limit (106751)
    but rounds hours and minutes down, rejecting a sliver of legal values
    (23 hours' and 1427 minutes' worth). Safe direction -- nothing that passes
    can throw -- but not exact, and only the days branch has a test, with no
    boundary case

StorageDeviceSetState set recursion has no cycle guard
  - collectDevices and the level-1 branch of selectDeviceWithSpace recurse
    through memberSets without a visited-set or decreasing-level check, and
    the memberSets/parent invariants are documented as unenforced
  - Pre-existing shape -- selectDevices does the same -- but
    collectMemberDevices now runs it on every migration poll pass, so a
    malformed set graph would spin rather than fail
