DataObject TKVL test suite sometimes reports hung tests during full test runs though it still succeeds. Although
apparently not flaky, it suggests that these tests may be taking an inordinately long time to complete. Investigate
to see if these tests are slower than they should be and where the hung transactions are occurring. Determine if
this is purely a test issue that can be fixed or if there may be an underlying system issue that needs to be addressed.

"Hung Test" prints now also appear occasionally in TKVLBatchSuite and AppendIntegrationSuite since stores began
holding requirement locks. They come from finalization actions waiting ~2.5-3.2 s on lock contention and retry
backoff; the tests pass. Investigate together with the DataObject TKVL item above: determine whether the backoff is
too conservative or whether finalization actions collide more than they should.

Fixed (2026-11-06): JVM SIGSEGV in librocksdbjni at `rocksdb::WriteBatchInternal::Count`, from
BufferedConsistentRocksDB.commitOnPool, seen twice in full `sbt test` runs. BufferedConsistentRocksDB.close() released
the database and the next WriteBatch as soon as no operation was inside begin/endOperation, but a commit still queued
on the pool, or one past its write, then read the freed nextBatch in its chaining step. close() now waits until no
commit is queued or in progress, and is idempotent. Covered by the two close tests in BufferedConsistentRocksDBSuite.
The bug predates the host refactor; the store executors only changed how often closes overlap commits.

--- Mid Term ---

Isolate every device's I/O, and detect and handle hung devices
  - Devices can hang for long durations, and every read and write to a hung device can hang indefinitely.
  - Today some I/O pools span devices: FSIF's I/O pools and the shared RocksDB engines. A single hung device can
    freeze all of those threads and effectively hang the whole host.
  - Every thread that touches a device must belong to a small set dedicated to that device alone, so a hung device
    stalls only its own stores. This needs a comprehensive plan covering every path that reaches a device: backend
    I/O, opens, the per-device CRL (docs/superpowers/specs/2026-11-07-per-device-crl-and-commit-ordering-design.md),
    rebuilds, transfers, markers and DurableFiles.
  - It also needs a plan for detecting device errors and hangs and taking appropriate action. One option:
    - Write `<host-root>/suspected-bad-device.yaml` naming the device, then restart the host process. A restart is the
      only guaranteed way to clear every thread and all in-memory state.
    - At startup the host sees the file and refuses to load the device's stores.
    - It then runs diagnostics to decide whether to put the device back into service or alert the user.
  - Automatically failing the device is a possible option, but it needs a cautious, well-thought-out plan. A bug could
    trigger false positives, and a systemic issue could fail stores automatically until pools drop below threshold
    (see the correlated "lost store" item below).
  - Until then, a transaction waiting on an in-flight commit to a hung device waits as long as the device hangs. The
    per-device CRL design accepts that.

Device CRL recovery runs on the host control thread
  - DeviceDiscovery opens and recovers each device's CRL (up to num-streams x file size, 3 x 300 MB by default) on
    aspen-host-control at startup and adoption. On HDD that can take seconds, stalling all other device management on
    the host. Move the open off the control thread (as BackendOpener does for FSIF opens) and post the result back.
    Fold into the device I/O isolation item above.

Off-device CRLs
  - A reasonable host configuration puts the CRLs of HDD devices on an NVMe device, so already-slow media is not
    written twice. Today a device's CRL is always `<device>/crl` (CrashRecoveryLog.deviceCrlDir); add a per-device
    location (e.g. a `crl-dir` in the device config, defaulting to the device directory).
  - Such a device cannot be adopted without a shutdown: its transaction state is not on the drive. The shutdown must
    write the CRL state onto the device as its final step before `shutdown.state`/`Shutdown`: copy it into a
    temporary directory on the device (`<device>/crl.incoming-<uuid>`), force the files and the directory, then
    atomically rename it to `<device>/crl` and force the device directory.
  - Adoption already requires `<device>/crl` when the device holds stores
    (docs/superpowers/specs/2026-11-08-unclean-device-adoption-design.md), so a drive pulled before that rename (or
    without a shutdown) is refused until it returns to its host. The device directory must therefore never carry a
    stale `crl` from an earlier move: delete it (durably) once the CRL lives elsewhere again.
  - The lost-CRL rule in DeviceDiscovery.openDeviceCrl (stores but no `<device>/crl`) must check the configured
    location instead.
  - An adopting host whose own config puts the device's CRL elsewhere may move it off the device: copy, force, then
    switch atomically, never leaving two live copies that could both be opened.
  - A restart on the same host after a shutdown, or a cancelled shutdown, must open whichever copy is current. Decide
    which copy wins and make the switch a single durable step.
  - CRL sizing (`crl-num-streams`/`crl-max-file-size-mb`) still travels with the device config, so a moved CRL opens
    with the same geometry.

System-level protection against correlated "lost store" declarations
  - The main source of data loss in a system like this is not hardware. It is a systemic bug that wrongly triggers
    one of the automatic lost-store paths: a store decides from local evidence alone that its content can't be
    trusted, marks itself `rebuild-required`, and is rebuilt from its peers.
    - One store wrongly declared lost costs only a rebuild.
    - The same bug firing on many stores at once is unrecoverable once the content is gone, because the peers the
      rebuild needs are the stores being thrown away. An upgrade to a version with a bad recovery check, a format
      misread, or a wrong validation bound would all do this.
    - Every automatic path is listed in the "Automatic lost store" section of
      server/store/backend/fsif/DESIGN.md (FSIF), plus the host-level `crl_save.log` loss paths (all backends).
  - This can't be fixed inside a store implementation, because each store sees only its own files. It needs a
    system-level check.
  - Store content must never be deleted automatically on purely local detection.
    - Today `Host.discardLostStore` moves the directory into the device's discard directory and deletes it at once,
      and `tryLoadDevice` empties that directory at startup.
    - Instead, move it to `<storage-device>/suspected-loss/<store-dir>-<uuid>` and keep it. Record why, when, which
      software version, and which check fired.
    - A rebuild can still proceed into a fresh directory, so availability doesn't depend on the decision.
    - A device CRL that fails to open is the same kind of local detection: `DeviceDiscovery.openDeviceCrl` moves it
      aside as `<device>/crl.lost-<uuid>` (up to num-streams x file size, 900 MB by default) and marks every store on
      the device rebuild-required. Those directories are kept forever today, deliberately: they are suspected-loss
      content, held for the system-level check below, never deleted on local evidence alone.
  - A higher-level system check decides what happens to suspected-loss content.
    - Look across the pool and the whole system for correlation:
      - several stores of one pool declared lost within a short window;
      - declarations clustered after an upgrade or on one software version;
      - the same check firing on many hosts;
      - more stores of a pool lost than its IDA tolerates.
    - When the pattern looks systemic, stop automatically declaring stores lost (or at least stop rebuilding over
      them), alert an operator, and keep every suspected-loss copy so a fixed version can recover them.
    - Only when the loss is judged isolated and not potentially systemic does the system issue an explicit
      deletion instruction for the retained content, through the usual object-based admin channel so it can't
      be lost.
  - Related: a rebuild that can't find enough healthy peers must fail loudly rather than rebuild from what's left.
  - Track suspected-loss space use per device, including `crl.lost-*` directories, since retained copies compete
    with live stores; see the "Full storage devices" item.

Follow-up to the DataObject TKVL: a RandomAccessReedSolomon-specialized, append-based DataObject node
encoding. Rather than a full overwrite on every kv insert/delete, append operations insert kv pairs
and tombstones until the object is full. If compaction frees up enough space, the object can be
overwritten and append operations can resume until a split is eventually required. The encoding is a
pluggable NodeEncoding so it plugs in without touching the tree logic in TierEngine.
  - Note that appending to the object saves write bandwidth but comes at the cost of increasing read
    bandwidth.
    - The implementation should balance the two. Rather than blindly appending, calculate the cost
      of doing a subsequent read when choosing to append or a compacted overwrite. There probably
      isn't a single solution that is ideal in all cases. If possible, design the code such that
      a plugin (or just a callback) can be provided that optimize to specific use cases but default to
      a good, general-purpose implementation.

On start, if the CRL is found to be corrupted. We would need to initiate a recovery process that checks
the metadata for every object in every store on the host to find objects that may have voted to commit,
crashed, and then come up with a missing CRL. Those mid-transaction objects wouldn't be recorded in the
error tree. The only way to recover would be to check every slice which reads reading the metadata for
all data objects and the metadata+KeyMetadata for all KeyValueObjects. Which would be hugely expensive.
Maybe a lightweight alternative would work. We could still send all Paxos state and data to the main CRL
but create much smaller logs on each device. Those logs just record the poolId+ObjectId of the objects
being modified by transactions plus tombstones for when the data is discarded. These would be small
enough that we could use a/b files for the logs. When one log is full, write the full compliment of
active transactions to the new log, flush it, then truncate the old log. Then if the main CRL fails,
we would know exactly which objects to repair without putting a large I/O load on the disk by double-writing
the data. Ultimately, we probably need a more robust solution than SimpleCRL.

Need a mechanism to handle "out of space" errors
  - Will present when we attempt to commit an object update to the store
    - Read-Only or out of space underlying media will cause it to fail
  - Will clog up the CRL if left untreated
  - Need a mechanism to properly handle backend commit failures (probably when out of space)
    - Immediately flip the store to read-only to prevent CRL clog
    - Keep CRL entries for read-only stores, do not discard on TxFinalized
    - continue serving updated state of objects that cannot be committed since we may have voted
      to commit them at write-threshold. Cannot lose the state or return pre-commit object state.
  - Might start with just relying on TransferStore to a device with space
    - Might be able to automate this eventually
  - Could set up "spillover stores"
    - Dedicated to hosting data for full stores
    - Lots of implications though, will require some thought
  - A late prepare arriving after the finalized status-cache entry expired can create a fresh Tx whose CRL save
    replaces a failed commit's retained entry (possibly without object data), and an abort of that Tx deletes it.
    The ErrorTree mark still covers it.

Adaptive store threading (parked, 2026-11-06): `StoreThreadPool.Adaptive` (code only) runs `StoreBalancer`; both
policies tried lost to a fixed 2-4 thread pool. Growing on busy time (>70%) grew to the cap, because busy time per
operation rises with each added thread, and evening out the loads spread light seqwrite load thinly: randrw 11,175/s
at 1,307 µs, seqwrite 1,363/s at 4,441 µs. Packing to 65% with growth on drain wait (>1 ms) did worse: randrw
8,004/s at 1,791 µs. Its problems, from its "Store threads:" log lines: idle load packs every store onto one thread,
so each burst starts there; once every thread is over target it stops balancing (four threads ran at ~90% while two
were at ~65%); it moves near-idle stores to no effect; seqwrite's normal drain wait (0.5-1.0 ms) is near the 1 ms
threshold, so it flipped between 2 and 4 threads. To revisit: consolidate only under sustained moderate load, even
out when every thread is over target, ignore near-idle stores, set congestion relative to each thread's normal wait,
and measure with longer runs and more than one workload.

DurableFiles' directory fsync is Linux-only
  - DurableFiles.syncDirectory opens a directory with FileChannel READ and forces it. Only Linux makes
    that a real directory fsync. Windows refuses to open a directory as a channel, so syncDirectory is a
    no-op there (one warning logged) and renames and removals of markers, CRL save files and store
    directories can be lost on power loss. macOS accepts it but the JDK issues a plain fsync, not
    F_FULLFSYNC, so entries can sit in the drive's write cache.
  - Windows fix: NTFS has no directory fsync, but a rename can be made durable itself. Use JNA to call
    kernel32 MoveFileExW(src, dst, MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH); WRITE_THROUGH
    makes the call return only once the rename is flushed to disk. Route DurableFiles.writeWith's rename
    and the store-directory moves (rebuild finish, transfer-in promotion, discard) through it, and make
    syncDirectory a no-op on Windows without the warning. For removals (DurableFiles.remove), open the
    directory with CreateFileW(GENERIC_WRITE, FILE_FLAG_BACKUP_SEMANTICS) and call FlushFileBuffers on
    the handle, or replace the remove with a write-through rename of the file into a discard directory.
    File data itself is already handled: FileChannel.force maps to FlushFileBuffers on Windows.
  - macOS fix: via JNA, call fcntl(fd, F_FULLFSYNC) on the directory and on each forced file instead of
    relying on FileChannel.force.

Full storage devices: keep stores serving and route around them system-wide
  - Once Paxos decides commit, every store must apply the update. If the backend cannot write it (device
    full), Tx.commitComplete currently ignores the error and drops the CRL object data, losing the slice.
  - Preallocation is not the answer: stores are deliberately over-allocated on a device and rebalanced as
    they grow, and some backends (e.g. RocksDB) cannot preallocate at all. It must be solved at the system
    level for every backend.
  - A full store must NOT be taken offline. If every device fills at once, that takes the whole pool offline.
    Instead:
    - The backend freezes in-progress writes (completions held, CRL data retained) and keeps serving reads.
    - A higher-level check notices the device is full and its stores start voting to abort transactions.
    - Clients/transaction drivers know which stores are full, do not send them writes, and rely on entries in
      the missed-update (error) tree to repair those slices once the store is writable again.
    - Writability returns when a rebalance moves the store to a device with free space, or when other stores
      migrate off the device. Frozen writes then resume, followed by repair of the missed updates.
  - FSIF (docs/superpowers/specs/2026-10-29-fsif-backend-design.md) implements only the backend side: freeze
    writes on ENOSPC, keep serving reads, retry until space returns.

Traceless commits follow-ups (minor, from the 2026-11-08 reviews):
- TracelessCommits entries are one per transaction (not merged per object like ErrorTree entries), but only for
  commit voters that sent no TxCommitted (all silent stores when the driver did not count the votes), so an offline
  store gets none. A voter that keeps missing errorTimeout under allocation-heavy load still grows the tree. Watch it.
- No repair proof compares a KV object's min/max/left/right (the object-level proof is a RevisionLock), and a
  SetMin/DeleteMin/... without a required revision is a traceless change that `deletesKeys` does not flag. Check
  whether such updates occur and, if so, how a store that misses one is repaired.
