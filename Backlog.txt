A tiered-list join racing a scan surfaces as a spurious filesystem error
  - KeyValueListNode.fetchContainingNode scans right along the bottom tier and fails on any read
    error. A join deletes the right-hand node in the same transaction that rewrites the left
    node's right pointer, so a scan that read the left node just before the join reads a deleted
    node and fails with InvalidObject. A retry from the top of the tree would succeed
  - Directory (retryUntilSuccessfulOr, retryCreation, insert, rename) and the AmoebaNFS rename
    turn FatalReadError into StopRetrying, so the race reaches the NFS client as an error
  - MetadataTree is unaffected (it never deletes, so its lists never join).
    MissedUpdateFinalizationAction's errorTree insert is affected but keeps retrying, since its
    handler retries everything except UnknownStoragePool and TransactionCreationError
  - Fix in the traversal (restart from the root on InvalidObject during a right scan) rather than
    in each caller, so that StopRetrying.unlessCollision becomes usable for these sites too

Follow-ups from parallel store transfers
  1. SetRebalanceDurableTask passes can overlap (wake() plus the poll, no single-flight
     guard). Add boundedSingleFlight (maxInFlight 2, arm the poll at pass start).
     MigratePoolToSetDurableTask lost its end-of-pass wakeup because its guard dropped a
     tick that fired before the pass released (fixed: run() now arms the poll on every call). SetRebalanceDurableTask does NOT have
     that race today, since with no guard no tick is ever dropped and every pass ends in
     scheduleRecheck, a re-entry, or finish. Adding the guard here WOULD introduce it, so
     arm the poll at the start of every call (as the migration task's run() does) in the
     same change. finishOk also should cancel pollTask, as the migration task's now does
  2. Stale resume of a promoted aborted copy: after a crash or StopRetrying, a re-transfer
     to the same destination resumes the old marked copy (Host.startStoreTransferIn's
     resume path). Carry the transfer UUID in the device entry, or discard a marked
     finalPath whose entry is absent
  3. A retry to a different device on the same host waits up to one device poll. Drop
     tracked attempts for a store this device's remote records TransferringIn from a
     different toDeviceId
  4. AspenClient.abortStoreTransfer nudges the destination host even when the entry was not
     ours or the destination is tombstoned; no test for the 'already completed' no-op nudge
  5. TransferStarter: a failed Future from start is ambiguous (document it); RolledBack is
     returned even when the abort was a no-op; TransferBackoff has no jitter and does not
     use FiniteDuration
  6. Rebalance minors: requiredSize falls back to 0; one random candidate per poll; the
     classify traverse is unbounded and each ready transfer reads the whole pool per poll
     (use runBoundedParallel); a stuck Rebuilding entry keeps the task InFlight forever
  7. Migration: a selection failure (AllocationError) does not back off
  8. Tests: a rebuild landing on a device other than the planned destination is untested;
     the 'no competing transfer' check is a single snapshot after a fixed sleep;
     failAndDrain/completeRebuild are duplicated across suites; no isSafe test for a
     width-1 pool
  9. The CLI transfer-store (cmdline/Main.scala ~1976) bypasses TransferSafety. Add a comment
     that it is an operator override that can push a pool below the floor
  10. The createSecondDevice test harness hangs for Replication pools with
      writeThreshold <= width/2 (tried (5,1), (5,2), (6,2), (6,3)). Those shapes are invalid
      IDAs, not a harness bug; see "Invalid IDA thresholds" below
  11. Pre-existing: when the destination finishes after a tombstoned source's entry was
      already drained, Host.updateStateForTransferredStore falls through to PoolRepointed
      and loads a copy the pool does not name

StoragePool.getState() and dropCachedState() are now dead API
  - SimpleStoragePool caches its StoragePoolState at construction and
    dropCachedState() has never had a caller, so the cached copy was a
    permanent snapshot of where the stores were when the client first
    touched the pool
  - Both stale-mapping consumers were fixed to use
    AspenClient.getStoragePoolState instead: transferStore and
    StoreManager.startStoreTransferOut. A survey of src/main and src/test
    found no remaining getState() callers
  - storagePoolCache still memoises the SimpleStoragePool instance, but its
    other construction-time fields (ida, maxObjectSize, allocStrategy,
    allocStrategyConfig, pointer) are immutable per pool and no consumer
    reads a store-to-device mapping from them
  - So this is now a cleanup, not a correctness issue: either delete
    getState()/dropCachedState() or wire the invalidation up

Possible bug in AmoebaFS
  - Looks like UnlinkFileTask may double-decrement the inode number
  - prepareUnlink method decrements the inode number and creates the UnlinkFileTask atomically
    if the refcount is zero.
  - The task always decrements the refcount as the first step
  - Need to verify that this is a flaw and look for cases where the task doing the decrement is
    valid. If never valid, just skip the decrement step and move on to freeing resources.
