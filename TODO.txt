
Malformed YAML escapes Main's catch block as a raw SnakeYAML stack trace
  - The catch around the cfg.mode dispatch matches YamlFormat.FormatError, ConfigError,
    TimeoutException, and IllegalArgumentException. A syntactically broken config raises
    none of them: SnakeYAML throws YAMLException subclasses -- ScannerException,
    ParserException, ComposerException -- and FormatError covers only Aspen's own
    validation, i.e. an empty document or a missing/misshapen field
  - loadYamlString's scaladoc in YamlFormat already documents this exact trap. Main is
    the caller it warns about, and it catches the wrong thing. loadYamlFile, which is
    the overload the CLI actually reaches via BootstrapConfig.loadBootstrapConfig,
    behaves the same way but carries no such warning -- worth copying the note over
  - Costs more than a stack trace. The exception unwinds out of main, so neither
    drainAndShutdown() nor System.exit(exitCode) runs, and the drain is what lets a
    nudge sent moments earlier survive process exit. Shell status is still nonzero
    because the JVM exits 1 on an uncaught exception, so this is lost cleanup and bad
    diagnostics rather than a wrong exit code
  - Ordinary to hit: a truncated or half-edited bootstrap config does it. scopt's
    validate only checks that the file exists, not that it parses
  - Fix is a narrow "case e: YAMLException" clause alongside the existing four.
    Deliberately not NonFatal: that would swallow genuine bugs into a one-line message,
    and an unexpected exception should stay loud
  - Affects every command taking a <bootstrap-config-file>, plus host, which loads both
    the host and bootstrap configs inside host()

  - Safety check reassignment to same set. No-op in this case
  - MigratePoolToSetDurableTask
    - register with system task executor at time of creation
  - Always reassign each store to a new device and move it
  - Keep it simple.
    - Optimize for not moving existing stores that are already in the set later
  - Must support assignement to level 1+ sets in addition to level 0
    - Ideally the design and implementation will be the same for both
      - Try to minimize and isolate any differences if the code cannot be made identical
  - Durable task selects a device for a store, calls transferStore, polls for
    completion then moves to next store. On complete, update PoolState to say
    migration status is Complete
    - protect against pileups while polling
    - protect against case where source and destination devices are the same
      - No-op in this case (already complete)
