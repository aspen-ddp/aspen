MetadataManager silently drops parked messages when a resolving pool lookup
names a host it has never looked up
  - startPoolLookup's Success branch (MetadataManager.scala:254-257) hands each
    store's queued messages to the store's host, but only if that host is already
    in `hosts`. The None branch does nothing, so the queue is discarded
  - stores += sid -> se.hostId runs first, so later sends to that store recover.
    Only the already-queued messages are lost
  - pendingPoolLookups -= poolId also runs first, so hasParkedMessages goes false
    and the exit drain reports success on a message that was dropped, not sent.
    awaitPendingMessagesSent's scaladoc names the failed-lookup case but not this
    one, because this one is a bug rather than an accepted limit
  - Candidate fix: in the None branch, start a host lookup for se.hostId and hand
    it the storeQueue instead of dropping it

StoreManager.activeDeviceChecks is keyed by device id only, and load state can
now change while a check is in flight
  - A CheckStorageDevice for a device not yet on disk takes checkStorageDevice's
    None branch and leaves a lookup in flight. If the config then appears and a
    later event loads the device before that lookup completes, the later event's
    checkStorageDevice is skipped by the guard, so the device is not checked
    until the next periodic CheckAllDevices
  - The stale None-branch callback also adds the now-loaded device's stores to
    offlineStores. Benign today because handleEvent matches stores.get first, but
    newly possible: before runtime device discovery a device could not go
    unloaded -> loaded with a check in flight
  - Candidate fix: re-read storageDevices.get(storageDeviceId) inside the
    callback rather than branching on it before starting the lookup

Reassignment of a pool to a new set:
  - MigratePoolToSetDurableTask
    - register with system task executor at time of creation
  - Always reassign each store to a new device and move it
  - Keep it simple.
    - Optimize for not moving existing stores that are already in the set later
  - Durable task selects a device for a store, calls transferStore, polls for
    completion then moves to next store. On complete, update PoolState to say
    migration status is Complete
    - protect against pileups while polling
    - protect against case where source and destination devices are the same
      - No-op in this case (already complete)

StoreManager.checkStorageDevice leaks its activeDeviceChecks guard on a
synchronous throw
  - The entry is added before client.getStorageDeviceState is called. Both
    outcomes of the returned Future release it, and so does a throw out of the
    callback, but a throw from getStorageDeviceState itself (before the Future
    exists) leaves the device wedged for the life of the process
  - Low probability; not guarded because the fix wants a seam that lets a test
    make the call throw

For maximum recovery speed, DurableRecoveryManagerTask
  - Delegates restore operations to groups of workers
  - Workers restore objects
     - Store the results locally (not re-erasure coded)
       - Could use a RocksDB-like backend. Key = ObjId + PoolIndex
     - Update dist datastructure noting their location
  - End-location downloads rebulit slices as they're created
