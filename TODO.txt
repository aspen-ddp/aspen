Need a reliable, system-level distributed DurableTask execution strategy
  - For focused things that need to happen but isn't tied to a host and the result is not needed
    - Example: Migrating a pool to a new device set
  - Goal is to spread the execution of these tasks across hosts so as to avoid overloading any one node
  - Implement SystemTaskExecutorService (subclass of DurableService)
    - Global singleton that is always running
      - Register this service in Bootstrap.scala like we do with RebalancingDurableService
    - tkvl of tasks to execute
      - Key = UUID, Value = objectPointer
    - service slow polls tkvl for new tasks for reliability
      - Uses NewSystemTaskAdded(uuid, pointer) message for performance
    - service caches a list of all host UUIDs
      - refreshed every 30 mins
    - On New Task Detected
      - Randomly select an online host
      - Send ExecuteSystemTask(uuid, pointer) message to host
    - Wait 30 seconds then start polling the task state object
      - If object deleted, task is complete. Discard state
      - If the revision hasn't changed in 45 seconds, reassign the task to a new host
    - All periodic operations need to guard against pileups
      - System can experience long periods where objects are not writeable or readable
      - Use util.ignoreExtraCallsWhileRunning or BackgroundTaskManager.scheduleNonConcurrentPollingTask
        or something similar
    - Each host listens for ExecuteSystemTask messages
      - Upon reception, load and start executing the task
      - Immediately use a transaction to VersionBump the task state object
      - hosts have a background task that runs every 15 seconds.
        - task does a VersionBump transaction on all system task state objects it's currently running
          - This is effectively a "heartbeat" to tell the system durable service that the host is alive
            and actively executing the task
    - On task completion
      - Delete tkvl entry of the DurableTask
      - Send SystemTaskComplete(uuid) to SystemTaskExecutorService
    - Add an AspenClient.createSystemDurableTask(taskTypeUUID, initialState: Map[Key, Array[Byte]]): Future[Unit]
      - retry until successful

    - register with system task executor at time of creation
  - Always reassign each store to a new device and move it
  - Keep it simple.
    - Optimize for not moving existing stores that are already in the set later
  - Durable task selects a device for a store, calls transferStore, polls for
    completion then moves to next store. On complete, update PoolState to say
    migration status is Complete
    - protect against pileups while polling
    - protect against case where source and destination devices are the same
      - No-op in this case (already complete)

Consider removing usage of invalidateTransaction in favor of just throwing
exceptions.
  - May be needed in some contexts but probably ought to be avoided when
    possible
  - Makes it difficult to detect problems and recover from them
  - Hides the source of the error
  - Limited to just a single error per tx setup

Need a mechanism to handle "out of space" errors
  - Will present when we attempt to commit an object update to the store
    - Read-Only or out of space underlying media will cause it to fail
  - Will clog up the CRL if left untreated
  - Might start with just relying on TransferStore to a device with space
    - Might be able to automate this eventually
  - Could set up "spillover stores"
    - Dedicated to hosting data for full stores
    - Lots of implications though, will require some thought

  - Optionally able to be attached to "things of interest"
    - Such as an AllocationGroup storage changing by 0.5%
  - When an "event" triggers:

For maximum recovery speed, DurableRecoveryManagerTask
  - Delegates restore operations to groups of workers
  - Workers restore objects
     - Store the results locally (not re-erasure coded)
       - Could use a RocksDB-like backend. Key = ObjId + PoolIndex
     - Update dist datastructure noting their location
  - End-location downloads rebulit slices as they're created

  + End-location can be throttled so as not to overload bandwidth
  + Data can be rebuilt at maximum speed (no choke points)
  + Rebuilt data can be read from dist data structure at a speed penalty
