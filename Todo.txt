PRIORITY 4: liveness (hangs, stalls, livelocks)
-----------------------------------------------

4.2 [RB-W14] A rebuild-complete removal whose unlink succeeded but whose directory sync failed leaves the store
    unserved until a restart. PLAUSIBLE. Effort S. rebuild-process.md.
    DurableFiles.remove unlinks, syncDirectory throws, clearRebuildCompleteMarker returns false and the copy is kept
    offline for the Completed Rebuilds pass, which selects only stores whose marker still exists. The old copy is
    released meanwhile.
    Fix: the Completed Rebuilds pass also retries removals it or the Adopt branch left pending (or any offline Active
    store with no marker), and the retry syncs the directory even when the marker is already gone.

4.3 [RB-W13] A transfer onto a device whose store path holds a copy of an earlier tenancy never starts.
    PLAUSIBLE. Effort S. rebuild-process.md.
    Host down while device D holds an unretired finished rebuild or a rebuild-required copy; replaceRebuild moves the
    store elsewhere, then a transfer moves it back (D's entry TransferringIn). No pass clears the path (Deleted Stores
    needs no entry, retireForeignCopy needs Rebuilding, Completed Rebuilds needs Active), so StoreTransfers.startIn
    logs "store path already exists" at every check until an operator aborts.
    Fix: in startIn, retire (StoreCopies.retire) a copy at the path carrying rebuild-complete or rebuild-required,
    then start once the path is clear. It must retire before the transfer can make the entry Active:
    markRebuiltStoreActive adopts an Active entry without an episode check (cross-document-review.md 2.2).

(SL-W9, a device without room for the CRL replacing its lost one, is in Backlog.txt's systemic-loss entry.)


PRIORITY 5: performance and hygiene
-----------------------------------

5.1 [Q-W14] A lock-order waiter withholds colliding lock-only votes it would never wait for.
    CONFIRMED. Effort S. transaction-requirements.md.
    Tx.lockWaitBlocked asks wouldWaitFor, which tests the lock collision but not the Frontend.changes filter that
    awaitLockHolders applies, so lock-only votes (a vdisk fence lock, repair proofs) wait up to CollisionWait and then
    vote abort needlessly.
    Fix: skip a waiter none of whose changed objects this transaction changes.
