- Store transfer cannot tolerate lost or reordered messages. Investigate, and develop a new
  implementation if confirmed.

  TransferringOut pipes `jar --create` output to the destination as a series of 1 MiB
  StoreTransferData host messages over the data port. A zero-length chunk marks the end.
  TransferringIn writes each chunk straight into the stdin of the `jar` extraction process, in
  the order the chunks arrive. There are no sequence numbers, acknowledgements or
  retransmissions. Aspen's network layer is allowed to drop messages, so:

    - A dropped data chunk silently corrupts or truncates the extracted store.
    - A dropped end marker leaves the transfer hanging until some timeout notices.
    - The QUIC plugin round-robins large messages across several streams. The 1-byte end marker
      would also travel as a datagram. So chunks can arrive out of order, which ZMQ's single
      TCP connection never allowed. That corrupts the archive even when nothing is dropped.
    - A chunk is dropped whenever the sender outruns the connection's buffer budget, which is
      exactly what a bulk transfer does.

  Separately, TransferringOut.readThread reuses one `buff` array for every full chunk, so a
  chunk still queued for sending can be overwritten by the next read. ZMQNet races on this
  today, and the QUIC plugin's zero-copy send makes it far more likely. Use a fresh array for
  each chunk.

  The unused `storeTransferPort`, present in host config, HostState and the CLI, suggests a
  dedicated transfer channel was intended. That is one option for the new implementation, along
  with a sequenced, acknowledged, flow-controlled protocol over the data port.

- Client read completion does O(object size) work inline on the network thread. Move it off the
  QUIC event loop, or make it cheap.

  QuicNet runs every MessageHandler callback on a Netty event loop, so
  BaseAspenClient.receiveClientResponse -> ReadManager.receive -> BaseReadDriver.receiveReadResponse
  now runs there, holding the driver's lock, for every ReadResponse:

    - BaseObjectReader.receiveReadResponse decodes each store's state (createObjectState) as its
      response arrives. For a KeyValue object that is a full decode of the store's slice.
    - DataObjectReader.restoreObject calls ida.restore. For ReedSolomon that is an erasure decode of
      the whole object.
    - On success BaseReadDriver logs `dos.data.hashString` at info. DataBuffer.hash copies the entire
      payload with getByteArray and then CRC32s it, so a 32 MiB read costs a 32 MiB copy and a
      32 MiB checksum on the loop just for a log line.

  While that runs, every other connection on the same loop stalls, heartbeats and keepalives
  included. The TxManager side (TransactionResolved / TransactionFinalized) only completes promises
  and is fine. Options: hand ReadResponses to the client's ExecutionContext before restoring, drop
  the hash from the log line or compute it only at trace.
