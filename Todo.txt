Per-device CRL follow-ups (final review of the per-device CRL branch, 2026-11-07):
- `<device>/crl.lost-<uuid>` directories (a lost CRL moved aside) are kept forever, up to num-streams x file size
  each (900 MB by default). Tie them into the suspected-loss retention policy (Backlog: correlated "lost store"
  declarations), or delete them once the device's stores are rebuilt.
- A failed device-CRL `dropStore` for a transferred-away store is retried only in memory (DeviceReconciler); a
  restart forgets it and the entries stay live and uncounted. Only a dead CRL thread makes a drop fail today.
- StoreRouter.crlLoaded removes `crl_save.log` with a plain os.remove that does not make the removal durable. After a
  crash a resurrected stale save file is re-saved over newer device-CRL state for the same TxIds on the next load.
  Use DurableFiles.remove. Predates the per-device CRL branch.
- A store closed with its entries left live (transfer-out save failed; closeUnloaded with dropDurably = false)
  releases its admission charges, so those live bytes go uncounted until the store loads again. Bounded and rare.
- StoreRouter.install replacing a loaded store never closes the old Frontend, so its admission charges leak and the
  new Frontend charges recovered transactions again. Reachable only through a direct Host.loadStore (tests) today.
- DeviceReconciler's leftover-entry drop reads the store's entries when it runs. A store transferred back onto the
  device while a stalled drop is pending could lose its new entries. Theoretical (a transfer takes far longer).
- extractUnloaded has a window between its async read and its delete in which a load of the same store would have its
  recovered entries deleted. No production path loads an offline TransferringOut store.

Adopt a storage device without a clean shutdown. Once each device carries its own CRL (see
docs/superpowers/specs/2026-11-07-per-device-crl-and-commit-ordering-design.md), the common case should be: yank a
drive out of a running or crashed machine, plug it into another host, and have it adopted and put back into service.
A shutdown first is still required when the device's CRL is not physically on the device. A reasonable host
configuration places the CRLs of HDD devices on an NVMe device to avoid double-writing to already slow media; for such
a device, the shutdown must write its current CRL state onto the drive in preparation for the physical move.

Potential hole in transaction recovery. Scenario, a Tx starts and reaches a commit decision. A store that voted to
commit crashes and recovers after the transaction was finalized and expunged from the transaction cache. Enough stores
fail to put the object at read-threshold and the store's pre-committed state is now required to restore the object.
It's transaction recovery process kicks in and attempts to resolve an abort. If an abort decision is reached and it
drops the pending update, the object is lost forever. Potential simple fix: if the current revision of the object
matches that of the transaction (and equivalent for KeyValue updates) then vote to commit (it already has). The
recovering store then correctly applies its updates and the commit becomes a no-op for the other stores.

Store commit delay FSIF commits seem to be taking longer than they should when backed by NVMe media. Investigate the
timing of commits.

QUIC applies the idle timeout (`QuicNet`: three heartbeats unless `QuicConfig.idleTimeout` is set) during the
handshake too. In the tests a CPU-starved handshake outlasted 1.5 s and the dial closed, so on a host starved for
longer than its idle timeout every dial fails until the load drops. Check whether production hosts need a handshake
allowance separate from the idle timeout.

Fixed (2026-11-06): JVM SIGSEGV in librocksdbjni at `rocksdb::WriteBatchInternal::Count`, from
BufferedConsistentRocksDB.commitOnPool, seen twice in full `sbt test` runs. BufferedConsistentRocksDB.close() released
the database and the next WriteBatch as soon as no operation was inside begin/endOperation, but a commit still queued
on the pool, or one past its write, then read the freed nextBatch in its chaining step. close() now waits until no
commit is queued or in progress, and is idempotent. Covered by the two close tests in BufferedConsistentRocksDBSuite.
The bug predates the host refactor; the store executors only changed how often closes overlap commits.
