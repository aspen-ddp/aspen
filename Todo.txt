[ ] Track down and fix the cause of the flaky test suite

    `sbt test` fails intermittently with a single failure in a timing-sensitive suite.
    Measured 2026-09-15: RebalancingServiceSuite failed 2 of 4 full runs on unmodified
    main (e8891c0), and 2 of 4 on a feature branch off it. Same suite, same rate on both
    trees. Measured 2026-09-02: SimpleCRLSuite failed 1 of 4 on merged main;
    RebalancingServiceSuite failed 1 of 4 on 4e6a828. Every one of these passes 100% when
    the suite is run standalone.

    Passing standalone but failing under a full run points at cross-suite interference
    rather than a bug inside the suite itself -- either load-sensitivity in the timing
    assertions, or state leaking from a suite that ran earlier. There is precedent for
    the latter: a leaked BackgroundTaskManager from a repair suite once broke
    RebalancingServiceSuite deterministically, and the fix was sequencing cleanup in
    .andThen rather than onComplete.

    Worth doing properly. The current cost is that every full-suite failure needs a
    baseline comparison against an unmodified tree before it can be believed, which is
    both slow and an invitation to wave off a real regression as "just the flake."

    Suggested first steps:
      - Capture the actual assertion failure. `sbt test | tail` truncates it; redirect the
        whole run to a file and grep for the suite name.
      - Run RebalancingServiceSuite immediately after each other suite in turn to find
        which predecessor triggers it.
      - Audit BackgroundTaskManager and any other shared scheduler for cleanup that isn't
        sequenced before the next suite starts.
