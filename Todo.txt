HostObjectCache is one `synchronized` cache shared by every store; with stores on parallel threads it is the likely
next contention point (see docs/superpowers/specs/2026-11-05-host-refactor-design.md).

Potential problem with rapid transactions. If we have a store backend that commits slowly, we could get a queue of
pending commits if we allow the next transaction on an object to commit before the current, in-flight commit
completes. In the pathological case, this could overflow the CRL. We need some mechanism to prevent the next transaction
from committing while the current one is in-flight. We could just not release the locks until the commit operation
completes but that's not ideal in that the subsequent transaction could "conflict" with the previous transaction in
the sequence, which doesn't make logical sense. The alternative would be to delay processing the transaction until
the commit completes. Usually, commit operations are fast, 10s of milliseconds, but they can experience random long
delays so buffering of high-transaction volume could be a concern. We are allowed to drop messages though so a
dropping solution could be incorporated into the solution.
