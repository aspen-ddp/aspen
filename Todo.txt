Transactions spanning objects in more than one StoragePool always abort
  - Found while writing the FSIF integration test. Pre-existing since the initial import; no existing test covered it
    because every allocating test uses the bootstrap pool.
  - Cause: Frontend.scala:88-90 builds each Tx with only txd.allHostedObjects(storeId), which TransactionDescription
    (:92) filters to the store's own pool. Tx.scala:114 then passes the full txd.requirements to
    RequirementsChecker.check, whose getState (RequirementsChecker.scala:31) throws MissingObject for any object not
    loaded. Tx.scala:124 votes abort whenever that list is non-empty, so every store votes abort on a requirement for
    an object in another pool.
  - This breaks the core pattern of allocating in one pool and storing the pointer in an object in another (e.g. the
    radicle or a TKVL node in a different pool).
  - Needs a design decision: only the primary pool's stores take part in Paxos, so decide which stores check which
    requirements (e.g. each store checks only the requirements for objects it hosts) and confirm the commit/abort
    decision stays correct.
  - Add tests that allocate in a non-bootstrap pool and link the pointer from an object in another pool. Once fixed,
    FsifIntegrationSuite can link its objects from the radicle instead of relying on the allocation tree.

StoreRepairer leaves missed-update (errorTree) entries behind after a successful repair
  - Found during the FSIF integration test. Pre-existing and not FSIF-related.
  - The delete at StoreRepairer.scala:140-146 is guarded by TimestampLessThan(key, os.timestamp), which fails only
    when entry.ts < os.timestamp (RequirementsChecker.scala:266-270). So once the object is updated again after the
    entry was written, the entry is never cleared, even when the repair brings the store fully current. This is
    likely under append-heavy workloads, where a store that missed one update goes on to apply later ones.
  - The guard's semantics also look inverted relative to its own doc comment: the comment says to keep the entry when
    a new miss lands after the read, but the check passes in exactly that case (entry newer than the object).
  - StoreRepairerSuite's "repaired and the entry removed" test passes only because it seeds the entry after the
    object's last update.
  - Decide the intended rule, fix the guard, and add tests for an object updated after its entry was written.
  - The intended context here is that the repair operation executes while live operations are being carried out. A
    repair operation may be started and the object will be restored with a timestamp of time t. When the repairer goes
    to delete the entry from the repair tree, it can only do so if the timestamp of the error tree entry is less than
    or equal to the timestamp of the repaired slice t. If an update to the object completed between the beginning of the
    repair operation its completion, the timestamp in the repair tree would be greater than that of the repaired object.
    That would mean that the repair operation restored the object to a less-then-current state and a new repair
    operation is needed. A repair operation can only delete an entry from the repair tree if the timestamp of the
    repaired object is equal to or greater than the timestamp of the repair tree entry.

FixedSizedIndexFileAllocationStrategy
  - Use a KeyValue object to hold segments of an allocated indicies bitmap
    - 100Gib of 1Mib segments is 102400 indicies - 12k allocation bitmap
  - Can use a bitmap KeyValue object to hold 100 1k segments of the bitmap
  - Allocator chooses one at random for allocating. Therefore low chance of collision
  - *** Note that this choice must be cached in the Transaction instance
    - When attempting to allocate multiple objects from the same pool in the transaction, we need to re-use
      this same bitmap. Only choose another if it is full.
    - We'll also need to be able to register a callback to be called at the beginning of the transaction build
      process.
      - This will aggregate all the allocations into a list of Insert operations with key revision guards
        and adds an update to the KeyValue object to the transaction
  - deleteObject method will need to register a DurableTask to clear the bitmap entry exactly once
    - Can't use a finalization action for this since they can run multiple times. A possible scenario is
      it runs on one store and clears the bit, the index is re-allocated, then the finalization action runs
      again on another store and clears the bit again while the new allocation is still valid.
  - Add this allocation strategy and a pointer to a KeyValue object with the KeyValue content holding the
    zeroed bitmaps to the StoragePoolState object of new pools being created with the FixedSizeIndexedFile
    backend.
