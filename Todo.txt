Examine the existing object read implementation. I believe RefcountUpdate losses are okay as the all transactions
updating objects are required to have a timestamp higher than that of the object being updated (verify this). If

I'm not entirely sure how to handle this. In the scenario where a transaction commits, the store in question doesn't
votes to commit but crashes before it learns the commit/abort decision and recovers after the transaction has been
forgotten and enough other stores are offline to the point where the commit should be applied to the recovering store,
the current implementation will result in an abort decision. In that case, the other read-threshold - 1 stores will
contain no entry for the key (or will contain a re-written key who's revision will not match that of the recovering
store. Check my logic but I think it is safe to abort the transaction and discard the delete because there are two
cases, in one, the other stores have no key. In which case the key is unrecoverable which is what the delete intended.

behind and will be marked in the error tree for recovery. The read stalls until an up-to-date store comes back online
which is intended behavior. If that logic holds, then nothing needs to be done.

Fixed (2026-11-06): JVM SIGSEGV in librocksdbjni at `rocksdb::WriteBatchInternal::Count`, from
BufferedConsistentRocksDB.commitOnPool, seen twice in full `sbt test` runs. BufferedConsistentRocksDB.close() released
the database and the next WriteBatch as soon as no operation was inside begin/endOperation, but a commit still queued
on the pool, or one past its write, then read the freed nextBatch in its chaining step. close() now waits until no
commit is queued or in progress, and is idempotent. Covered by the two close tests in BufferedConsistentRocksDBSuite.
The bug predates the host refactor; the store executors only changed how often closes overlap commits.
