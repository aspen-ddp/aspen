Background
----------
Intermittent `sbt test` failures (RebalancingServiceSuite, SimpleCRLSuite) were measured at
~50% per full run in Sept 2026 on an otherwise idle machine. Two causes were found and fixed in
cc74578, both confirmed from instrumented logs:

  - testSweptSetsCount was a JVM-wide static. sbt runs suites in parallel in one JVM and every
    test system carries its own RebalancingDurableService, so sweeps from DurableServiceSuite
    etc. were counted by RebalancingServiceSuite. Now keyed per service state object.
  - RebalancingDurableService.reconcile() checked "is a sweep due" against state read before
    it claimed the sweep. A reconcile that read state while the previous sweep was recording
    itself could claim after that sweep finished and sweep a second time. Now re-reads after
    claiming.

What is NOT known: whether those two fixes account for the whole original flake. Four idle
runs on the pre-fix tree passed 4/4, so the original rate could not be re-measured.

Reproducing under load: saturate the cores with busy loops, then run the full suite, e.g.
    PIDS=""; for i in $(seq 24); do sh -c 'while :; do :; done' >/dev/null 2>&1 & PIDS="$PIDS $!"; done
    sbt test > run.log 2>&1 ; kill $PIDS
Track the PIDs and kill by PID. `pkill -f` matching the loop's own command line also kills the
invoking shell. Full saturation (24 loops on 24 cores) is much harsher than the original flake
conditions and produces failures that may not be bugs (see item 3). Redirect the whole run to
a file and grep for FAILED; `sbt test | tail` truncates the assertion text.

Method that worked: add a temporary System.err.println at the suspect point (include the
service state pointer, System.identityHashCode of the instance, and thread name), reproduce
under load, group the log lines by state pointer. Revert the instrumentation afterwards.

[x] 2. SimpleCRL: a delete in an older log entry erased a newer re-save  (FIXED 2026-10-20)

    Root cause: LogEntry.loadStaticEntryContent did `rstate.txs -= txid` for each deletion.
    Recovery loads entries newest to oldest, so an older entry's delete removed a re-save already
    loaded from a newer entry. The backward walk only reaches the delete's entry when it shares an
    entry with a live transaction (oldestEntryNeeded points there), and that batching depends on
    whether the IO thread has processed WriteComplete before the delete arrives -- hence
    intermittent (1 in ~1000 idle, more under load). A production bug: a transaction re-saved
    after deletion could vanish on restart.
    Fix: deletes apply only to saves in the same entry and in older entries.
    Test: SimpleCRLSuite "Re-saved transaction survives recovery ..." forces the batching by
    holding the writer thread in a completion handler (deterministic; failed 3/3 before the fix).
    Not explained: the earlier "Recycle Streams" failure (seen once under saturation). It may be
    the same family (recovery of deletes/recycling); re-check whether it still appears.

[x] 2b. SimpleCRL dropped a re-save of a deleted id without running its handler  (FIXED 2026-10-20)

    LogEntry.addTx skipped a save whose id was deleted earlier in the same unwritten entry, but
    the completion-handler registration was inside the same `if`, so the caller never got a
    callback. Deletions are final, so the skip is right; the handler now always queues and fires
    when the entry holding the delete is durable.
    Test: SimpleCRLSuite "Save after a delete in the same unwritten entry is skipped but reports
    success" (fails without the change).
    Note: only the same-entry case is skipped. A save of a deleted id that arrives after the delete
    entry was written is still logged (the CRL keeps no memory of deleted ids), and recovery now
    keeps it (item 2's fix) so recovery matches the live state. Tests "Delete and re-save same
    transaction ID" and "Re-saved transaction survives recovery ..." pin that behaviour; if
    deletions should be final across entries, they and that behaviour should be reconsidered.

[x] 3. The service executor can run two instances of one service at once  (INVESTIGATED 2026-10-20)

    Instrumented create / lease-loss in SimpleDurableServiceExecutor (since reverted) and ran
    the full suite 11 times at 24 busy loops. Findings:
      - Every duplicate is lease expiry, not a duplicate claim. doRenewal sees the entry expired
        (by 1-160ms) because a 2s lease with a 200ms renewal cannot be kept when the process is
        starved -> handleLeaseLoss shuts the instance down -> the next scan re-claims and builds
        a replacement. ~20 executors per loaded run did this.
      - The attemptClaim overwrite hypothesis is REFUTED: 0 of 781 creates found an existing
        owned instance. No guard is needed there.
      - The old instance is shut down at loss, so two instances overlap only while a sweep that
        began before shutdown is still in flight (sweepOneSet checks `stopped` only at its
        start). A cross-instance guard would be needed to remove that entirely; production
        tolerates it (enrollment is revision-checked and idempotent).
    Change: RebalancingServiceSuite's executor fixture now uses a 30s lease / 1s renewal (the
    suite does not test lease timing). "sweep skips a level-1 set" failed 1 of 5 loaded runs
    before and 0 of 5 after -- a small sample, so treat as likely rather than proven.
    "SimpleCRL Recovery From Multiple Streams" under load (INVESTIGATED, test bug, CRL is correct):
    the test calls deleteTransaction() then save() back to back and expects them in separate log
    entries (stream 2). Stream.writeEntry runs the entry's completion handlers BEFORE it posts
    WriteComplete to the CRL thread, so the test thread can enqueue both requests first; the CRL
    thread then batches them into one entry, which still fits in stream 1 (assert at line 285 saw
    1, not 2). Repro loop of the scenario: 0/400 failures idle, 30-36/400 under saturation, all
    failures were the batched ordering. Recovery was checked after every run and was correct in
    all 400, including the batched ones. Fix: the test now fills stream 1 with an extra
    save+take first, so the stream-2 outcome holds whether or not the pair is batched (0/400
    under load, SimpleCRLSuite 3/3 under load + idle). Not changed: the handlers-before-
    WriteComplete order in Stream.writeEntry. It is harmless for correctness; swapping it would
    make batching deterministic for callers, but it is a CRL main-path change.
    "SimpleCRL Recycle Streams" (INVESTIGATED, test bug, CRL is correct): same family. The test
    does save(tx2); delete(tx2); take(); shutdown(). When the save is written alone, the delete
    sits in the next, unwritten entry, and shutdown() does not flush it, so recovery returns tx1
    and tx2 (2 txs, expected 1). Repro of the scenario: 1/400 idle, 30-31/400 under saturation;
    with a 50ms pause before shutdown 0/400. Fix: save again after the delete and wait for it
    (FIFO order means its entry holds the delete), then shut down. Dropping an unwritten delete
    at shutdown is fine for a crash-only design: recovery just re-offers the transaction.
    SimpleCRLSuite 31/31 on 3 loaded runs and 1 idle run after the fix (small sample).
    "Recovery From Multiple Streams" and "Switch Streams" also called i.crl.save() after
    i.crl.shutdown(). Not a CRL bug: the CRL thread has exited, so the request was never
    processed and the following currentStreamNumber assertion only re-read a stale field.
    Removed both calls and assertions. (A save after shutdown is silently dropped; fine for a
    crash-only design.)
    Remaining failures in those runs are item 4 (timeouts under saturation).

[ ] 5. Global test seams are reset only when a test succeeds

    RebalancingDurableService.pollPeriod (and the same pattern in FailedStorageDeviceDurableTask
    and MigratePoolToSetDurableTask) is a @volatile static that tests set and reset. In
    RebalancingServiceSuite the reset and exec.shutdown() sit in the `yield`, so a failed or
    timed-out test leaves the executor running and pollPeriod changed, which can cascade into
    later tests. Because suites run in parallel in one JVM, one suite's pollPeriod also leaks
    into every other suite's services while it is set.

    There is precedent: a leaked BackgroundTaskManager once broke RebalancingServiceSuite
    deterministically, and the fix was sequencing cleanup in .andThen rather than onComplete.

    Approach:
      - Move executor shutdown and the pollPeriod reset into an .andThen / equivalent that
        runs on failure too.
      - Better: pass pollPeriod through the factory or client instead of a static, as was
        done for the sweep counter, so concurrent suites cannot see each other's value.
