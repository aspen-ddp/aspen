- Store-transfer trailer could carry the archive length.

  The receiver's only completeness check is the 17-byte StoreId trailer
  (StoreTransferManager.TrailerSize), held back from the extractor and compared on EOF, plus the
  extractor's exit code. JDK SSLSocket treats a TCP FIN without close_notify as a normal EOF, so a
  sender crash looks like a clean end of stream. A false accept would need the archive to end with
  the StoreId bytes at exactly the point the connection dropped and jar --extract to exit 0 on
  the truncated input -- astronomically unlikely, and the design deliberately chose no
  length/checksum. Closing it is cheap, though: make the trailer the StoreId followed by an
  8-byte big-endian count of archive bytes sent (TrailerSize = 25); the receiver counts the bytes
  it forwards to the extractor and requires both to match. Optionally add a CRC32 of the archive.
  Update the wire-protocol section of
  docs/superpowers/specs/2026-10-22-store-transfer-tcp-design.md and the truncation tests.

- Client read completion does O(object size) work inline on the network thread. Move it off the
  QUIC event loop, or make it cheap.

  QuicNet runs every MessageHandler callback on a Netty event loop, so
  BaseAspenClient.receiveClientResponse -> ReadManager.receive -> BaseReadDriver.receiveReadResponse
  now runs there, holding the driver's lock, for every ReadResponse:

    - BaseObjectReader.receiveReadResponse decodes each store's state (createObjectState) as its
      response arrives. For a KeyValue object that is a full decode of the store's slice.
    - DataObjectReader.restoreObject calls ida.restore. For ReedSolomon that is an erasure decode of
      the whole object.
    - On success BaseReadDriver logs `dos.data.hashString` at info. DataBuffer.hash copies the entire
      payload with getByteArray and then CRC32s it, so a 32 MiB read costs a 32 MiB copy and a
      32 MiB checksum on the loop just for a log line.

  While that runs, every other connection on the same loop stalls, heartbeats and keepalives
  included. The TxManager side (TransactionResolved / TransactionFinalized) only completes promises
  and is fine. Options: hand ReadResponses to the client's ExecutionContext before restoring, drop
  the hash from the log line or compute it only at trace.
