- A destination crash between promoting a transferred store and the pool metadata commit leaves
  the store offline until an operator intervenes.

  On a successful transfer in, Host.startStoreTransferIn removes the transfer-out marker from the
  staged copy, os.moves it from <device>/transferring-in/<store> to <device>/<store>, and only
  then runs updateStateForTransferredStore to repoint the pool. If the destination host dies in
  that window (crash-only, so this is a normal event):

    - On restart tryLoadStore finds a complete store directory with no marker at the final path
      and loads it, even though the pool still names the source as the owner. Nothing routes
      to it, but the copy is live on a device the metadata says does not own it.
    - The device check still sees the store as TransferringIn, but startStoreTransferIn refuses
      to start because finalPath already exists, logging "store path already exists" on every
      check. The metadata step is never retried.
    - The source's copy stays offline behind its own transfer-out marker, and the abandoned
      transfer-out pass will not reinstate it because the entry is not Active.

  This ordering predates the TLS/TCP transfer work (the old TransferringIn did the same), but it is
  now the main remaining crash hole in transfers. Recommended fix: promote with a distinct
  "transferred-in" marker instead of no marker. tryLoadStore skips directories carrying it (like
  the transfer-out marker). startStoreTransferIn, on finding finalPath with that marker, skips
  the byte transfer and resumes at updateStateForTransferredStore. The marker is removed only on
  TransferOutcome.PoolRepointed, immediately before loadStoreById; on SourceRestored the whole
  directory is discarded as today. Add a Host test that injects a "crash" after promotion (fresh
  Host over the same root) and checks that the store is not loaded and the metadata step resumes.

- An abandoned transfer in is never cleaned up on the receiving host.

  When the source device is declared failed mid-transfer, Host.abandonTransferIn rewrites the
  device entry but does not touch transferringIn, pendingStartTransfers or the
  StoreTransferManager registration for that store. Since a receiver registration has no timeout
  of its own (the old 30 s no-data timer is gone), the consequences last for the life of the
  process:

    - The pending-start retransmit task keeps sending StartStoreTransfer to the dead source host
      every 30 s.
    - transferringIn still holds the store, so startStoreTransferIn will never start a new
      transfer of that store onto this host until a restart.
    - A partial staging directory under transferring-in/ may be left behind until a later transfer
      of the same store replaces it.

  Recommended fix: when abandonTransferIn's transaction commits, drop the store's
  pendingStartTransfers and transferringIn entries, cancel any scheduled transfer-in retry, and
  have the service drop the registration (add a StoreTransferService.cancelTransferIn(storeId)
  that fails the pending future, aborts any live connection/extractor and removes the staged
  directory). Also have the delayed retry re-read the device entry and give up if the store is no
  longer TransferringIn, so a retry scheduled before the abandon does not send one more request.
  Separately, consider sweeping stale transferring-in/ directories at device load.

- Store-transfer trailer could carry the archive length.

  The receiver's only completeness check is the 17-byte StoreId trailer
  (StoreTransferManager.TrailerSize), held back from the extractor and compared on EOF, plus the
  extractor's exit code. JDK SSLSocket treats a TCP FIN without close_notify as a normal EOF, so a
  sender crash looks like a clean end of stream. A false accept would need the archive to end with
  the StoreId bytes at exactly the point the connection dropped and jar --extract to exit 0 on
  the truncated input -- astronomically unlikely, and the design deliberately chose no
  length/checksum. Closing it is cheap, though: make the trailer the StoreId followed by an
  8-byte big-endian count of archive bytes sent (TrailerSize = 25); the receiver counts the bytes
  it forwards to the extractor and requires both to match. Optionally add a CRC32 of the archive.
  Update the wire-protocol section of
  docs/superpowers/specs/2026-10-22-store-transfer-tcp-design.md and the truncation tests.

- Client read completion does O(object size) work inline on the network thread. Move it off the
  QUIC event loop, or make it cheap.

  QuicNet runs every MessageHandler callback on a Netty event loop, so
  BaseAspenClient.receiveClientResponse -> ReadManager.receive -> BaseReadDriver.receiveReadResponse
  now runs there, holding the driver's lock, for every ReadResponse:

    - BaseObjectReader.receiveReadResponse decodes each store's state (createObjectState) as its
      response arrives. For a KeyValue object that is a full decode of the store's slice.
    - DataObjectReader.restoreObject calls ida.restore. For ReedSolomon that is an erasure decode of
      the whole object.
    - On success BaseReadDriver logs `dos.data.hashString` at info. DataBuffer.hash copies the entire
      payload with getByteArray and then CRC32s it, so a 32 MiB read costs a 32 MiB copy and a
      32 MiB checksum on the loop just for a log line.

  While that runs, every other connection on the same loop stalls, heartbeats and keepalives
  included. The TxManager side (TransactionResolved / TransactionFinalized) only completes promises
  and is fine. Options: hand ReadResponses to the client's ExecutionContext before restoring, drop
  the hash from the log line or compute it only at trace.
