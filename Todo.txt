FSIF throughput after device I/O isolation (measured 2026-11-24, docs/host-threading-measurement.md "Device I/O
isolation: before/after")
  - What degraded: FSIF needs many more I/O threads per device than before to reach the same throughput. Before
    (fd82a6f3), every FSIF store shared one host-wide `sharedIo` pool of max(4, CPUs) = 24 threads and a
    `sharedSerial` pool of max(2, CPUs) = 24 threads. After, each device has its own `dataEc` of
    `--device-io-threads` threads and one serial thread.
    - At the design default of 4 data threads, a 16-store pool on one device was 20-28% slower:
      - randrw-verify read IOPS 409 against 510;
      - seqwrite 91 against 108 MiB/s;
      - two devices 386 against 499 read IOPS and 89 against 122 MiB/s;
      - fsyncs about 2x longer.
    - Throughput rises steadily with the thread count (2, 4, 8, 12 threads give 322, 409, 430, 528 read IOPS). The
      default was raised to max(4, CPUs/2) (`DeviceIo.defaultDataThreads`), which brings throughput back to baseline.
    - Still worse at the default: randrw fsync avg 816 ms against 472-540 before (one device). seqwrite fsync and
      every clat number are equal or better.
    - Cost of the workaround: a host with many devices now runs CPUs/2 data threads per device. Idle pools time out,
      but a busy host has far more FSIF threads than before.
  - Cause (investigated 2026-11-24, microbenchmark; the fio/TCMU runs were not repeated):
    - Each store has its own journal, and each batch is one blocking write + force on a data thread
      (`JournalWriter.send`). The vdisk workload commits every transaction on all 16 stores, so each transaction
      needs 16 fsyncs on the device. Each appends to its file, so each fdatasync is an ext4 jbd2 commit (~10 ms
      here; ext4 batches concurrent fsyncs into one commit, max_batch_time 15 ms). ext4 merges only the fsyncs in
      flight together, so with N data threads a transaction pays about 16/N fsync rounds, and reads queue behind
      the forces on the same pool.
    - Thread wake/sleep cost is not the limit: with threads >= stores the pool wait is 0.1-0.5 ms against a 10 ms
      force.
    - Microbenchmark: 16 real FsifBackends on one ThreadedDeviceIo, NVMe/ext4, randrw-like (50/50 ranged writes on
      all stores and reads on 10, depth 8). ops/s by data threads: 1: 49, 4: 131, 12: 374, 16: 602, 24: 767, 32: 751.
      Read latency 39 ms at 4 threads, 6.3 at 16, 1.7 at 24. Journal force ~9.7 ms at every count; at 4 threads
      tasks waited ~32 ms for a pool slot.
      - The threads needed follow the store count: 8 stores gave 619 ops/s at 8 threads, 762 at 12.
      - Serial threads (1 against 4, at 4 and 16 data threads) made no difference: the serialEc suspect is ruled out.
      - One store on one thread gave 962 ops/s, more than 16 stores on 32 threads.
      - A plain-Java model: one shared journal file on one thread did 490 tx/s (1355 preallocated, overwrite-only);
        16 separate journals peaked at 381 with 16 threads. Preallocated per-store journals: one fsync took 1.4 ms
        against 5 ms, but 16 concurrent ones degraded past 8 threads (each issues its own device flush).
    - This explains the measured numbers: the old 24 shared threads covered 16 stores; CPUs/2 = 12 does not, hence
      the remaining randrw fsync gap. Untested prediction: `--device-io-threads=24` closes it.
    - Chosen direction: one journal per device, shared by its stores (device-level group commit), preallocated so a
      force changes no metadata. Design in progress.
  - Caveats before investigating:
    - Every number above was taken with vdisk-server's full piece scan on cached reads, which made each cache-hit read
      60-70 us slower on a fragmented block; it is fixed in dda89905.
      - That fix sped the baseline's RocksDB randrw by ~45%.
      - FSIF was not re-measured after it, so the FSIF gap and the thread count needed may differ now. Re-measure
        both trees first, with HEAD's vdisk-server on both.
    - Cross-session drift is ~15% (two baseline sessions gave 510 and 585 read IOPS). Run the trees back to back,
      alternating, three or more runs each.
    - Host and vdisk-server share the machine in this benchmark. Watch host CPU: more device threads can starve
      vdisk-server, which is what produced the remaining RocksDB no-fsync gap.
    - Avoid the TCMU 30 s SYNCHRONIZE CACHE timeout (ext4 goes read-only, on both trees) by laying out small files one
      at a time.
  - Why thread count matters to FSIF: its file I/O is blocking (reads, writes and forces each hold a thread). The
    queue depth a device sees is therefore bounded by its data threads, and 16 stores on one device share them, where
    before they shared 24.
  - Suspects to check:
    - The single serial thread per device (`serialEc`). Before, serial drains had a 24-thread pool. Now all of a
      device's stores' `SerialExecutor` drains share one thread, including compaction's inline truncate (Task 4
      ruling: kept inline on serial). A drain that waits behind another store's truncate or force delays commits. Try
      2-4 serial threads per device: per-store ordering lives in each `SerialExecutor`, not the pool.
    - Forces: the longer randrw fsync suggests forces queue behind reads and writes on the same small pool. Look at
      whether one store's force waits for unrelated data tasks; a separate small force pool per device is an option.
    - The read gate (`DeviceIo.beginRead`/`endRead`, FsifBackend ~1584-1600) and the `DeviceIoObserver` bookkeeping
      on every data task. The RocksDB root-cause work found no per-read cost from these, but FSIF tasks are smaller and
      more numerous, so confirm with a profile.
    - `SizeTrackedFiles` (estimateSize without I/O): check that its accounting adds no synchronization on the write
      path.
  - How to look:
    - Use the measurement doc's capture-job.sh/analyze.py: thread dumps and BackendTiming's "store commit
      (FsifBackend)" against "fsif commit". The gap is time spent outside FSIF.
    - Add a per-device data-pool queue length and wait time; the observer's `inFlight` and `completed` give a start.
    - Use JFR or async-profiler on the host under randrw at 4 and 12 threads. Compare thread states (blocked in
      pread/pwrite/fdatasync against waiting for a pool slot).
    - A microbenchmark of 16 FSIF stores' commits through one DeviceIo, at 4 and 24 threads and at 1 and 4 serial
      threads, isolates the host from vdisk.
  - Potential fixes, roughly cheapest first:
    - Size the serial pool above 1.
    - Scale a device's data threads with the number of stores on it, not CPUs. FSIF wants concurrency per device
      queue, which depends on how many stores share the device.
    - Group commit: batch forces per store, or per device across stores, so fewer threads sit in fdatasync.
    - Asynchronous file I/O (io_uring, or AsynchronousFileChannel where it is truly async), so queue depth no longer
      costs a thread per outstanding operation. This is the structural fix, and the larger change.
