The TKVL as it currently exists is useful but has poor storage efficiency an identical data structure
composed of DataObjects would be useful for low-contention use cases like single-writer. Proposed
solution, generalize the TKVL code such that the important logic such as content management,
tree navigation, splitting/joining, etcetera can be shared by trees built on top of DataObjects
as well as KeyValue objects. KeyValue pairs stored in DataObjects wouldn't have identical semantics
as they lack the metadata associated with KeyValueObject pairs but most of the navigation and
management code should be able to handle that. The end-user facing API cannot hide that but
the behind-the-scenes logic probably can.
Thoughts on implementation:
  - The Root object probably gains an Enum saying which kind of tree it stores
  - It'd be really nice if the DataObject TKVL implementation could be further specialized for
    RandomAccessReedSolomon encoded objects.
    - Rather than a full overwrite on every kv insert/delete, append operations could be used insert kv pairs
      and tombstones until the object is full. If compaction frees up enough space, it can be
      overwritten and append operations can resume until a split is eventually required.

Need KeyValueListNode & TKVL prepareUpdates(inserts: List[(Key,Value)], deletes: List[Key]): Future[Unit]
  - Applies all changes in a single transaction
  - May want to consider reimplement individual prepareInsert/prepareDelete operations in terms of this
    more general-purpose method
  - First step is to create a list of insert/delete operations sorted by key
  - At KeyValueListNode level, just scan right and update/split/join nodes along the way
  - At TKVL level, we can branch off and parallelize operations as we descend the tree
    - can split off a subset of operations that will apply to a down pointer, and split off another set that
      applies to another down-pointer. Both descent operations will result in a pointer so upper tiers return
      sequences of futures to lower-level operations completing.
    - Should result in good performance

Need to add an upper-tier node caching capability to speed up future tree navigations
  - Upper tiers change very slowly so caching can be very beneficial
  - Cache misses don't affect correctness because we can always scan right on a tier
  - No one solution will be best in all cases so this should be an interface with pluggable implementations
  - Start super simple with a fixed LRU cache of 5 nodes for each tier-1+
    - TKVLs default to this implementation
    - No caching of tier-0 nodes
    - Whenever a scan-right operation is done in a tier, drop the cache on the tier above it.
      - reread the root if the scan-right is done on the top tier
