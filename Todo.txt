Test environment:
- TestNetwork creates missed updates that nothing repairs. The client sends a transaction's prepares one store at a
  time and the test messenger drains events after each, so the first stores can decide and finalize before the last
  sees its prepare (~100 such missed updates per DirectorySuite run). The test client has no opportunistic rebuild and
  no repairer runs, so a later transaction requiring state two stores each missed aborts on every attempt (a hang).
  TestNetwork.batchClientPrepares (opt-in, off by default) delivers a client's prepares together; only the
  unlink-step tests in DirectorySuite use it. Enabling it globally (or batching in ClientTransactionDriver) breaks
  AppendIntegrationSuite / RangedWriteIntegrationSuite (they rely on a store falling behind) and 4
  PoolObjectAllocatorSuite tests (not investigated). Decide whether to make it the default, with those suites making
  a store fall behind explicitly (dropTxMessage).

Pre-existing amoebafs bugs found during the replay-pins work:
- Cross-node rename whose delete joins into the target node updates that node twice, so the rename deterministically
  fails (liveness bug, SimpleDirectory.prepareRename).
- Directory.prepareMove / AmoebaNFS.move read iptr outside the retry; the delete pins the fresh revision but does not
  check that the entry still holds iptr.
- SimpleDirectory.prepareDelete reads tree.get and the containing node separately; a NothingToDelete between them
  leaves the transaction unpinned (enforcement then fails it).
