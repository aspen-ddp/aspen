Add an EventLogging system composed of the following parts
 - An EventLogEntry class that is comprised of
   - An 8-byte timestamp containing the number of nanoseconds since the epoch
   - A type UUID
   - A byte array of data for the entry
 - An Event trait or abstract class containing:
   - An 8-byte timestamp containing the number of nanoseconds since the epoch
   - A type UUID
 - An abstract EventFactory for use with the RegisteredTypeFactory that contains
   - def createEvent(e: EventLogEntry): Event
 - An abstract event EventObserver comprised of
   - observedTypes: Option[Set[UUID]] - used to say which event types this observer is interested in. If None, the
     observer is interested in all event types
   - def observe(e: Event): Unit
 - An abstract EventObserverFactory for use with the RegisteredTypeFactory that contains:
   - def createEventObserver(typeUUID: UUID, configData: Array[Byte]): EventObserver
 - An EventLogDurableService
   - The state object for the durable service contains:
     - An "incomingEvents" TKVL. Event creators will insert new log entries by creating a random UUID to serve
       as the key and a serialized EventLogEntry as the value (use ProtocolBuffers for the EventLogEntry encoding
       to allow for easy extension in the future)
     - A "loggedEvents" DataObject TKVL where the key is the 8-byte timestamp of the lowest entry in log for a
       data object containing logged events.
     - A mapping between event type UUIDs and an internally-assigned 2-byte integer for that type UUID
     - A list of (event observer type UUID, Array[Byte])
     - A logObjectAllocatorUUID which will be the UUID of an ObjectAllocator for allocating DataObjects that will
       serve as the permanent home for logged events.
   - Behavior
     - At startup, load the UUID to internal integer map and create EventObservers for all the event observer type
       UUIDs (use the registered type factories and the associated config data array to create these instances)
     - The service polls the incomingEvents TKVL (and accepts a nudge message to do an immediate scan), copies all
       found events over to the loggedEvents tree, and deletes the entries from the incomingEvents tree
     - Whenever a new event type UUID is found, it assigns it the next highest internal id and updates the map in the
       state object
       - The purpose of this is to reduce storage size. UUIDs are used to ensure no two ids will ever accidentally
         collide but we will never have very many distinct event types in the same system. Likely less than 100 in real
         systems but we'll use a 2 byte integer just to be safe.
     - The loggedEvents tree is a tree of timestamps pointing to DataObjects containing log entries
       - The key is the smallest timestamp contained within the object
       - The object content is just a list of serialized EventLogEntry instances (but using the 2-byte integer in place
         of the full UUID) that are sorted by timestamp from smallest to largest
       - Note that most of the inserts will go to the right-most object however, it is possible for delayed events to
         be entered into the incomingEvents tree so updates to older objects must be supported. We do not need to
         optimize for this though so the likely case will be to simply "split" the node similar to we do for TKVL nodes.
       - Each data object should be compressed with the zstd-jni library and kept to approximately 2mb in size. This is
         a soft limit only. If a massive log entry causes an object to greatly exceed this soft limit, that's fine.
     - After each event is written to the loggedEvents tree, the service will use the registered type factory system
       to create an Event instance for the entry and then pass the event object to all EventObservers that have the
       event's type UUID in its observedTypes set or if observedTypes is None (which indicates an interest in all
       Events)
     - Check the loggedEvents root and logObjectAllocatorUUID for a change in the object allocators to use and update
       internal state to use them if a new allocator has been assigned.
  - Add a SystemEventLog to the bootstrap process to ensure a default, system-wide event log is running at all times,
    like the Rebalance service. Default to allocating all objects from the bootstrap pool
  - Add an AspenClient.prepareSystemEventLogEntry(e: EventLogEntry): Future[Unit]
    - prepares a transaction for entering the log entry into the system's event log incomingEvents tree
    - the Future completes when the transaction is ready to commit
  - Add an AspenClient.logSystemEvent(e: EventLogEntry): Future[Unit]
    - thin wrapper calling prepareSystemEventLogEntry with a transaction and committing it. Do not automatically
      retry on failure and be sure the scaladoc calls this out.
  - Add an AspenClient.setSystemLogAllocator(objectAllocatorId: UUID): Future[Unit]
    - Verify that the supplied object allocator ID exists
    - Update the root of the loggedEvents TKVL to use the new allocator
    - Update the service's state to set logObjectAllocatorUUID to the new allocator
