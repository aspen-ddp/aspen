# Design: `create-storage-device` CLI command

**Date:** 2026-07-27
**Status:** Approved

## Goal

Add a CLI command, `create-storage-device`, that registers a new storage device
on an existing host and writes the device's on-disk config file so the host's
`StoreManager` will discover it.

Registration updates three objects in a single atomic transaction:

1. A new `StorageDeviceState` KeyValue object is allocated and registered in the
   `storageDevicesTree`.
2. The owning `HostState` is updated to include the new device.
3. The target level-0 `StorageDeviceSetState` is updated to include the new
   device.

The command creates no stores. Stores appear on the device later, when a pool is
assigned to it.

## Provisioning model

The device directory is **manually provisioned** before this command runs. In
production a real device is mounted at that location, or a symlink under the
host's `storage-devices/` directory points at the mount point. The generated
config file must land on the device itself, so the command never creates the
directory — it requires it to already exist.

## Approach

Three layers, following the split established by `create-device-set` and
`move-device-to-set`:

- **`AspenClient.createStorageDevice`** — the metadata transaction. It lives in
  `BaseAspenClient` alongside every other create, because `storageDevicesTree`
  is private there and all creates route through the `runCreate` seam.
- **`server.StorageDeviceManager.createStorageDevice`** — the orchestrator. It
  validates the directory and host config, calls the client, then writes the
  yaml. `StoreManager` will call this same function when device creation is
  automated, which is why it is not CLI-local.
- **`Main.create_storage_device`** — argument plumbing and error reporting only.

## Relevant existing facts

- **`StorageDeviceState`** is a **KeyValue object** whose state lives under
  `StorageDeviceState.StateKey`. Fields: `storageDeviceId`, `hostId`,
  `currentUsage`, `totalSize`, `stores: Map[StoreId, StoreEntry]`,
  `storageDeviceSet`. A new device starts with `0L, 0L, Map()`;
  `StorageDeviceUsageManager` fills in usage later.
- **`HostState`** is a **KeyValue object** with state under `HostState.StateKey`
  and `storageDevices: Set[StorageDeviceId]`. `addStorageDevice` returns an
  updated copy.
- **`StorageDeviceSetState`** is a **DataObject** with
  `memberDevices: List[StorageDeviceId]` and `level: Int`. Only level-0 sets
  hold devices. `StorageDeviceSetState.NotLevelZero` already exists from the
  `move-device-to-set` work.
- **`StorageDeviceConfig`** (`server/StorageDeviceConfig.scala`) holds
  `storageDeviceId` and `aspenSystemId`, serialises via `yamlConfig`, and is
  read by `loadHostConfig`. Its filename constant is
  `aspen-storage-device-config.yaml`.
- **`StoreManager`** scans `rootDir/storage-devices/` and calls `tryLoadDevice`
  on each **direct child**. `tryLoadDevice` requires the config file to be
  present and its `aspenSystemId` to match the running system, or it logs
  `"Storage Device found that does not belong to this Aspen system"` and skips
  the device.
- **`HostConfig.loadHostConfig(file)`** yields `hostId` and `aspenSystemId`.
- **`Main.resolveRef(ref, byUuid, byName)`** resolves a name-or-UUID argument.
- **`BaseAspenClient.createStorageDeviceSet`** is the canonical pattern for
  "allocate an object, register it in a metadata tree, link it into a parent,
  all in one transaction".

## Prerequisite: `hostState` naming fix

An earlier commit accidentally replaced many occurrences of `host` with
`hostState`. This branch fixes the config-facing instances, which are real API
and file-format surfaces:

| Location | Current | Corrected |
|---|---|---|
| `HostConfig.configFilename` | `aspen-hostState-config.yaml` | `aspen-host-config.yaml` |
| `HostConfig` yaml key | `hostState-id` | `host-id` |
| `HostConfig` doc comment | `name: bootstrap-hostState` | `name: bootstrap-host` |
| `BootstrapConfig` yaml key | `bootstrap-hostStates` | `bootstrap-hosts` |
| `BootstrapConfig` yaml key | `hostState-id` | `host-id` |
| `Main.scala` arg label | `<hoste-directory>` | `<host-directory>` |

Both files are generated by `./t bootstrap`, and the checked-in `demo/*.yaml`
files are already stale against the current `BootstrapConfig` format, so no
in-repo fixture breaks. Configs generated by a prior run must be regenerated or
hand-edited.

**Not included:** the same corruption reached comments and test names in the
TKVL suites, where the replaced word was often `node` rather than `host`
(`"Join on delete to empty hostState"`, `"Right hostState should have keys 3,
4"`), and `TransactionDriverSuite:152` where `host` was a verb
(`"poolIndex doesn't hostState a slice"`). Correcting those needs per-site
judgement and belongs in its own commit.

## Command

```
create-storage-device <bootstrap-config-file> <host-directory> <device-name> <set-name-or-uuid>
```

```
./t create-storage-device demo/bootstrap_config.yaml demo/node_a dev2 default-set
```

- `<bootstrap-config-file>` — connects the client, and supplies the expected
  `aspenSystemId`.
- `<host-directory>` — contains `aspen-host-config.yaml`; supplies `hostId`.
  Mirrors the `host` command, which also takes a host directory.
- `<device-name>` — the base name of the device directory. Because the directory
  is required to sit at a fixed location, the CLI accepts the name alone and
  resolves `<host-directory>/storage-devices/<device-name>`. The directory must
  already exist; see validation below.
- `<set-name-or-uuid>` — the target level-0 device set.

New `Args` field: `deviceName: String = ""`. Reuses the existing `hostDirectory`
and `deviceSetName` fields.

This is a CLI ergonomic convenience only. `StorageDeviceManager` still takes a
full `Path` and performs every check itself, because callers other than the CLI
— `StoreManager`, once device creation is automated — will pass paths directly.

The CLI needs no validation of its own: a name containing a separator
(`foo/bar`) resolves to a grandchild of `storage-devices`, `..` resolves outside
it, and an absolute path replaces the base entirely. All three fail the
manager's containment check.

Dispatch passes the loaded bootstrap config, as the `host` command does, because
the `aspenSystemId` check needs it:

```scala
case "create-storage-device" =>
  create_storage_device(bootstrapConfig, bootstrapConfigPath,
                        cfg.hostDirectory.toPath, cfg.deviceName,
                        cfg.deviceSetName)
```

### Shared directory-name constant

`"storage-devices"` is currently a bare literal in two places
(`Main.bootstrap:851` and `StoreManager:106`) and this change would add a third.
Introduce `StorageDeviceManager.StorageDevicesDirName = "storage-devices"` and
use it at all three sites.

## Components

### 1. `AspenClient.createStorageDevice`

New method on the trait beside `createStorageDeviceSet`, implemented in
`BaseAspenClient`:

```scala
def createStorageDevice(hostId: HostId,
                        deviceSetId: StorageDeviceSetId): Future[StorageDeviceId]
```

The device id is generated **once, outside** `runCreate`, so a retry reuses it
rather than leaking a fresh UUID per attempt — the same approach
`createStorageDeviceSet` takes with `sds.setId`.

```scala
val deviceId = StorageDeviceId(UUID.randomUUID())
val state = StorageDeviceState(deviceId, hostId, 0L, 0L, Map(), deviceSetId)

def onFail(err: Throwable): Future[Unit] = err match
  case e: NoSuchElementException => throw StopRetrying(e)
  case e: ReadError => throw StopRetrying(e)
  case e: StorageDeviceSetState.NotLevelZero => throw StopRetrying(e)

runCreate(onFail): tx =>
  given Transaction = tx
  for
    bsPool <- getStoragePool(PoolId.BootstrapPoolId)
    devPtr <- bsPool.allocator.allocateKeyValueObject(
                Map(StorageDeviceState.StateKey -> Value(state.encode())))
    _      <- storageDevicesTree.preparePut(deviceId.uuid, devPtr)

    hostPtr  <- getHostPointer(hostId)
    hostKvos <- read(hostPtr)
    setPtr   <- getStorageDeviceSetPointer(deviceSetId)
    setDos   <- read(setPtr)
  yield
    val hostState = HostState(hostKvos)
    tx.update(hostPtr, None, None,
      List(KeyRevision(HostState.StateKey,
                       hostKvos.contents(HostState.StateKey).revision)),
      List(Insert(HostState.StateKey,
                  hostState.addStorageDevice(deviceId).encode())))

    val setState = StorageDeviceSetState(setDos)
    if setState.level != 0 then
      throw StorageDeviceSetState.NotLevelZero(deviceSetId)
    tx.overwrite(setPtr, setDos.revision,
      DataBuffer(setState.copy(
        memberDevices = deviceId :: setState.memberDevices).toBytes))

    deviceId
```

Devices have no name and are not entered in the `namespacedRegistry`; the
UUID-keyed `storageDevicesTree` is the only registration.

`TClient.runCreate` is a plain `transact`, so integration tests exercise this
transaction directly with no stubbing. Because the method is concrete on
`BaseAspenClient`, no test client stub is needed.

### 2. `server.StorageDeviceManager`

New file, `src/main/scala/org/aspen_ddp/aspen/server/StorageDeviceManager.scala`.
A stateless `object`:

```scala
def createStorageDevice(client: AspenClient,
                        hostConfig: HostConfig,
                        hostDirectory: Path,
                        deviceDirectory: Path,
                        deviceSetId: StorageDeviceSetId,
                        aspenSystemId: UUID): Future[StorageDeviceId]
```

Validation runs first, entirely before the transaction, in this order:

| Check | Failure |
|---|---|
| `hostConfig.aspenSystemId == aspenSystemId` | `WrongAspenSystem(expected, found)` |
| device dir's parent is `<host-dir>/storage-devices` | `DeviceDirectoryNotUnderHost(dir, expectedParent)` |
| `Files.isDirectory(deviceDirectory)` | `DeviceDirectoryNotFound(dir)` |
| no `aspen-storage-device-config.yaml` present | `DeviceAlreadyConfigured(dir)` |

The parent comparison uses `toAbsolutePath.normalize` on both sides and does
**not** call `toRealPath`, so a symlink at `storage-devices/dev2` pointing at
`/mnt/disk2` passes the containment check. The subsequent `isDirectory` call
does follow the link, and the config file is written through it onto the device.
Only direct children are accepted, because `StoreManager` scans only direct
children.

Then, on success:

```scala
for
  deviceId <- client.createStorageDevice(hostConfig.hostId, deviceSetId)
yield
  val cfg = StorageDeviceConfig(deviceId, aspenSystemId)
  Files.write(deviceDirectory.resolve(StorageDeviceConfig.configFilename),
              cfg.yamlConfig.getBytes(StandardCharsets.UTF_8))
  deviceId
```

The new exception types live in the `StorageDeviceManager` companion.

**Ordering.** The transaction commits before the file is written. These two
cannot be made atomic. A crash between them leaves registered metadata with no
on-disk device: the device never comes online, nothing else references it, and
the operator can write the file by hand or re-run. The reverse order would let a
host load a device whose `StorageDeviceState` object does not exist, breaking
usage tracking. No compensating transaction is attempted.

### 3. `Main.create_storage_device`

Follows the shape of `move_device_to_set`: `configureLogging()`,
`createAmoebaClient`, `network.startIoThread(client)`, then

```scala
val hostCfg = HostConfig.loadHostConfig(
                hostDirectory.resolve(HostConfig.configFilename).toFile)

val deviceDirectory = hostDirectory
                        .resolve(StorageDeviceManager.StorageDevicesDirName)
                        .resolve(deviceName)

val f = for
  setId    <- resolveRef(setRef, StorageDeviceSetId(_), client.getStorageDeviceSetId)
  deviceId <- StorageDeviceManager.createStorageDevice(
                client, hostCfg, hostDirectory, deviceDirectory,
                setId, bootstrapCfg.aspenSystemId)
yield deviceId
```

reporting via `onComplete` and `Await.ready(f, Duration(30, SECONDS))`.

Success message:
`Created storage device <uuid> at <resolved-device-directory>`.

### Error reporting

| Cause | Message |
|---|---|
| `WrongAspenSystem` | `Error: host config belongs to Aspen system <found>, not <expected>` |
| `DeviceDirectoryNotUnderHost` | `Error: <dir> must be a direct child of <host-dir>/storage-devices` |
| `DeviceDirectoryNotFound` | `Error: storage device directory does not exist: <dir>` |
| `DeviceAlreadyConfigured` | `Error: <dir> already contains aspen-storage-device-config.yaml` |
| `NotLevelZero` | `Error: device set '<ref>' must be a level-0 (tier-0) set` |
| `NoSuchElementException` | `Error: host or device set '<ref>' not found` |
| `IOException` after commit | `Error: device <uuid> was registered but writing <path> failed: <msg>`, followed by a line telling the operator to create the file manually or remove the metadata and re-run |

The post-commit write failure must name the device UUID — it is the only handle
the operator has for recovery.

## Data flow

```
create-storage-device <bootstrap-cfg> <host-dir> <device-name> <set>
  -> Main.create_storage_device
       load HostConfig from <host-dir>/aspen-host-config.yaml
       device-dir = <host-dir>/storage-devices/<device-name>
       resolveRef(set, StorageDeviceSetId(_), client.getStorageDeviceSetId)
    -> StorageDeviceManager.createStorageDevice
         validate (4 checks, all pre-transaction)
      -> AspenClient.createStorageDevice(hostId, setId)
           runCreate -> single atomic tx:
             allocate KV obj  StateKey -> StorageDeviceState
           + storageDevicesTree.preparePut(uuid, ptr)
           + HostState              (tx.update, Insert on StateKey)
           + StorageDeviceSetState  (tx.overwrite, memberDevices += id)
         <- StorageDeviceId
         write <device-dir>/aspen-storage-device-config.yaml
    <- StorageDeviceId
  print "Created storage device <uuid> at <dir>"
```

No message is sent to the host. It picks up the device on its next scan of
`storage-devices/`, or at restart.

## Testing

### `StorageDeviceCreationSuite` (new)

Extends `IntegrationTestSuite`, alongside `StorageDeviceSetIntegrationSuite`.

- Creates the device: `getStorageDevicePointer(newId)` resolves, and the decoded
  `StorageDeviceState` carries the right `hostId` and `storageDeviceSet`, an
  empty `stores` map, and `0/0` usage.
- `HostState.storageDevices` contains the new id.
- The target set's `memberDevices` contains the new id.
- Two consecutive calls produce distinct ids, and both appear in the host and
  the set.
- `NotLevelZero` when the target set has `level != 0`.
- `NoSuchElementException` for an unknown host id.

### `StorageDeviceManagerSuite` (new)

Validation behaviour, using a temp directory tree. The negative cases need no
client.

- Rejects a device dir whose parent is not `<host-dir>/storage-devices`. Cover
  the three shapes a bad CLI `<device-name>` resolves to: a grandchild
  (`foo/bar`), a path escaping upward (`..`), and an absolute path.
- Rejects a nonexistent device dir.
- Rejects a dir already holding `aspen-storage-device-config.yaml`.
- Rejects a mismatched `aspenSystemId`.
- Accepts a **symlink** under `storage-devices/` that points at a directory
  elsewhere, and writes the yaml through it. This is the case the literal-path
  containment check exists to support.
- On success the written file parses back via
  `StorageDeviceConfig.loadHostConfig` with the returned device id and the
  correct system id.

### `MainSuite`

- `create-storage-device` parses into the correct mode with all four fields
  populated, `deviceName` holding the bare name.

### Rename coverage

- `HostConfig.loadHostConfig` round-trips `HostConfig.yamlConfig`.
- The equivalent round-trip for `BootstrapConfig`.

These prove the renamed keys stay consistent between writer and reader.

## Out of scope

- Creating or symlinking the device directory. That is the operator's job here,
  and the separate `add-storage-device` TODO item covers automating the link.
- Any CnC message telling the host to rescan.
- Creating stores on the new device; that happens when a pool is assigned.
- The comment-only `hostState` corruption in the TKVL and transaction test
  suites.
- `HostState.removeStorageDevice`, which uses `+` where it means `-`. A real bug,
  unrelated to this work, with no current caller.
